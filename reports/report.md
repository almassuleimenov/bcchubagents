### REQ-047 · HTTP 200 · стр. 162

### REQ-048 · HTTP 400 · стр. 163

> 400. Ответ в случае, если параметры запроса заполнены неверно.

- **D-007** 🔴 **Critical** · Контракт API · 📍 стр. 163 · REQ-048
  - **Цитата:** «400. Ответ в случае, если параметры запроса заполнены неверно.»
  - **Почему это дефект:** REQ-048 указывает, что при неверно заполненных параметрах запроса (например, некорректная сумма) должен возвращаться статус 400. Однако в примере успешного ответа (REQ-167) для статуса 200 приводится JSON `{"result":"ERROR","message":"Проверьте сумму"}`, что означает, что ошибка валидации параметров может быть возвращена со статусом 200, а не 400. Это прямое противоречие в обработке ошибок.
  - **Критерий:** ISO 29148 §5.2.6 consistent
  - **Как исправить:** При неверно заполненных параметрах запроса всегда возвращать соответствующий статус ошибки (например, 400 Bad Request) и не использовать статус 200 OK для передачи ошибок валидации.
  - <sub>Источник: LLM · CrossCheck · цитата: точное совпадение</sub>

### 4.4. Дефекты уровня набора и межтребовательные противоречия

- **D-008** 🔴 **Critical** · Противоречие · 📍 стр. 171
  - **Цитата:** «{"result":"ERROR","message":"Проверьте сумму"}»
  - **Почему это дефект:** Ошибка бизнес-валидации возвращается с HTTP-статусом успеха (2xx) и result=ERROR, при этом для неверных параметров уже объявлен 400. Клиент и мониторинг не смогут однозначно отличить успех от отказа; два способа сообщить об одной ошибке противоречат друг другу.
  - **Критерий:** IEEE 830 §4.3.4 consistent; RFC 9110 §15; ISO/IEC/IEEE 29148 §5.2.6 consistent
  - **Как исправить:** Возвращать 400/422 с единым форматом ошибки (например, RFC 9457 problem+json: code, message, field); 200 — только при успешном сохранении.
  - <sub>Источник: правило `API-200-WITH-ERROR` · подтверждено LLM · цитата: точное совпадение</sub>

- **D-009** 🔴 **Critical** · Контракт API · 📍 стр. 171
  - **Цитата:** «{"result":"ERROR","message":"Проверьте сумму"}»
  - **Почему это дефект:** Документ описывает возврат ошибки бизнес-валидации (например, неверная сумма) с HTTP-статусом 200 OK и полем `result: ERROR` (стр. 171), при этом для неверных параметров уже объявлен HTTP 400 (REQ-048). Это создаёт противоречие и неоднозначность: клиент и системы мониторинга не смогут однозначно отличить успешное выполнение от отказа, а также приводит к двум способам сообщения об одной и той же категории ошибок.
  - **Критерий:** ISO 29148 §5.2.6 (consistent), IEEE Std 830-1998 §4.3 (correct)
  - **Как исправить:** Унифицировать обработку ошибок: все ошибки бизнес-валидации должны возвращаться с соответствующим HTTP-статусом (например, 400 Bad Request или 422 Unprocessable Entity), а HTTP 200 должен означать только успешное выполнение операции.
  - <sub>Источник: LLM · CrossCheck · цитата: точное совпадение</sub>

- **D-040** 🟠 **Major** · Неполнота · 📍 стр. 26
  - **Цитата:** «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»
  - **Почему это дефект:** В документе отсутствует описание того, как обрабатываются сценарии, когда карта становится неактивной (например, заблокирована, срок действия истёк). Неясно, должны ли продолжать работать уведомления или настройки для такой карты.
  - **Критерий:** ISO 29148 §5.2.6 (complete)
  - **Как исправить:** Дополнить требования описанием поведения системы при работе с неактивными картами (например, блокировка уведомлений, невозможность изменения порога).
  - <sub>Источник: LLM · QualityFilter · цитата: точное совпадение</sub>

- **D-041** 🟠 **Major** · Непроверяемость · 📍 стр. 29
  - **Цитата:** «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».»
