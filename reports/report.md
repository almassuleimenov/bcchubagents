### REQ-005 · стр. 29

> На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».

- **D-005** 🟠 **Major** · Противоречие · 📍 стр. 29 · REQ-005
  - **Цитата:** «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».»
  - **Почему это дефект:** В требованиях к UI указано отображение суммы за месяц (REQ-005), однако метод сохранения API возвращает только параметры порога и признака включения без текущей суммы расходов (REQ-044), что делает невозможным рендеринг экрана мобильного банка.
  - **Критерий:** ISO/IEC/IEEE 29148:2018 §5.2.6
  - **Как исправить:** Добавить поле currentAmount в ответ метода API для передачи текущих расходов за месяц.
  - <sub>Источник: LLM · CrossCheck · цитата: точное совпадение</sub>

### 4.4. Дефекты уровня набора и межтребовательные противоречия

- **D-004** ⛔ **Blocker** · Противоречие · 📍 стр. 171
  - **Цитата:** «{"result":"ERROR","message":"Проверьте сумму"}»
  - **Почему это дефект:** Ошибка бизнес-валидации возвращается с HTTP-статусом успеха (2xx) и result=ERROR, при этом для неверных параметров уже объявлен 400. Клиент и мониторинг не смогут однозначно отличить успех от отказа; два способа сообщить об одной ошибке противоречат друг другу.
  - **Критерий:** IEEE 830 §4.3.4 consistent; RFC 9110 §15; ISO/IEC/IEEE 29148 §5.2.6 consistent; RFC 9457; RFC 9110 §9.2.1
  - **Как исправить:** Возвращать 400/422 с единым форматом ошибки (например, RFC 9457 problem+json: code, message, field); 200 — только при успешном сохранении.

#### InfoSec · Информационная безопасность — PCI DSS, ПДн

**Q-10.** Как обеспечить безопасность передачи идентификатора карты и единообразную защиту от несанкционированного доступа (BOLA) при запросах к чужим картам в соответствии с требованиями PCI DSS v4.0.1 Req. 3 и 6? <sub>(приоритет: Major)</sub>
- **Варианты решения:**
  1. Перенести cardId в тело POST-запроса (JSON body) и возвращать HTTP 403 Forbidden при попытке доступа к чужой карте.
  2. Оставить в query-строке, возвращать 404 Not Found согласно текущему описанию.
- **Рекомендация:** Вариант 1 (перенос в body и 403) — исключает утечку чувствительных данных держателей карт в логи прокси/серверов и предотвращает уязвимости Broken Object Level Authorization (BOLA).
- **Влияние на проект:** Изменится спецификация OpenAPI (перенос cardId из query в body), обработчики авторизации на бэкенде и логика возврата кодов ответа (403 вместо 404).
- **Было** (стр. 142): «cardId \| string \| 1–64 \| Да \| Карта клиента \| Идентификатор карты \| card_id»
- **Стало (EARS):** Если клиент запрашивает данные по чужой карте, то API должно вернуть HTTP-статус 403 Forbidden с телом ошибки по стандарту RFC 9457, а идентификатор карты должен передаваться в теле POST-запроса, исключая его попадание в query-строку.
- **Закрывает дефекты:** D-016, D-020
