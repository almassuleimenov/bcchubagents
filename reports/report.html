32 
33#### BPMN схема процесса

36#### Функциональные требования
37* **Ф-1.** Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸ включительно. По умолчанию уведомление выключено.
38* **Ф-2.** Месяц определяется по дате совершения покупки в Алматы. В расходы входят проведённые покупки. Возврат уменьшает расходы месяца исходной покупки. Переводы и снятие наличных исключаются.
39* **Ф-3.** Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент получает push. На карту приходится максимум один такой push за календарный месяц.
40* **Ф-4.** При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

D-003 · Blocker · Контракт API
стр. 104 · REQ-024 · RFC 9110 §9.2.1; RFC 9110 §9.2.1 (safe methods); ISO/IEC/IEEE 29148 §5.2.5 correct; IEEE 830 §4.3.1; ISO/IEC/IEEE 29148:2018 §5.2.5 (consistency); ISO/IEC/IEEE 29148:2018 §5.2.6; ISO/IEC/IEEE 29148:2018 §5.2.5 Completeness
Метод /alerts/saveLimit, который изменяет настройки пользователя, объявлен как HTTP GET (REQ-024). Согласно RFC 9110 §9.2.1, метод GET должен быть безопасным (safe) и не изменять состояние сервера. Использование GET для изменяющей операции является грубым нарушением стандарта и может привести к непредсказуемым изменениям состояния из-за кэширования или повторных запросов.
Исправить: Изменить HTTP-метод для операции сохранения порога на POST или PUT, которые предназначены для изменения состояния сервера.
D-004 · Blocker · Противоречие
стр. 121 · REQ-032 · RFC 9457; IEEE 830 §4.3.4 consistent; RFC 9110 §15; ISO/IEC/IEEE 29148 §5.2.6 consistent; RFC 9457 (Problem Details for HTTP APIs); ISO/IEC/IEEE 29148:2018 §5.2.5; RFC 9110 §15.3.1 200 OK, RFC 9110 §15.4.1 400 Bad Request, RFC 9457
Логика работы метода (REQ-032) указывает, что при отклонении суммы возвращается 'результат ERROR'. Однако в разделе 'Ответ' (стр. 151) указано, что 'Если результат 200 или 201 — успешный. Исправить: Исправить логику возврата ошибок: при отклонении суммы должен возвращаться HTTP-статус 400 Bad Request с соответствующим телом ошибки, а не 200 OK с result=ERROR.

D-053 · Minor · Противоречие
стр. 147 · REQ-039 · ISO/IEC/IEEE 29148:2018 §5.2.6 Consistency; IEEE 830 §4.3.4 consistent; ISO/IEC/IEEE 29148:2018 §5.2.5 (consistency); RFC 9110 §8.3
В разделе 'Request body' указан `Content-Type: application/json` (REQ-039), но сразу после этого следует утверждение 'Тело не используется' (REQ-040). Поскольку метод является `GET` (REQ-024) и использует `Query-параметры` (стр. 139), тело запроса действительно не должно использоваться, что делает указание `Content-Type` для тела запроса избыточным и потенциально вводящим в заблуждение.
Исправить: Удалить упоминание `Content-Type: application/json` из раздела 'Request body', так как тело запроса не используется для данного `GET` метода.
